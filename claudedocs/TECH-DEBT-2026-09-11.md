# Technical debt — MOTS Supplier Portal, 2026-09-11

## What was run, and what it was worth

The `tech-debt-tracker` skill's scanner was run first, over the whole repository. It reported
**124,451 debt items** and a health score of **0**. That number is not usable and should not be quoted.

The scanner reads every file it can open, regardless of type. Its top contributors were a Word
document, four Lighthouse JSON reports, `package-lock.json` and the OpenAPI baseline. Its
`todo_comment` rule matched the letters T-O-D-O inside compressed binary, producing findings like
`TODO/FIXME comment: bUg"bͿ2SAZU5$ʫAϕȪ`. Its `duplicate_code` rule, at a three-line minimum, flagged
95,787 items against a codebase whose duplication is already measured properly by SonarCloud.

Re-run against source only, with binaries and generated output excluded, it reported 9 TODO comments —
of which **all nine were false**: a `Stepper` status value legitimately named `todo`, and font binaries.

So the numbers below were measured directly rather than scanned. Each is reproducible with the command
beside it.

## What is actually true

### There are no TODO, FIXME, HACK or XXX markers in this codebase

Zero, across every `.cs`, `.ts` and `.tsx` file outside migrations.

```bash
git ls-files | grep -E "\.(cs|ts|tsx)$" | grep -v Migrations/ | xargs grep -nE "\b(TODO|FIXME|HACK|XXX)\b"
```

That is unusual and it is not an absence of debt. This repository records its debt in prose documents
and in comments that name the defect they exist for, which is why a marker-scanner finds nothing and
concludes the codebase is clean. It is the same failure mode the repository's own testing culture is
built against: a check that measures nothing looks exactly like a check that passes.

### No known vulnerabilities on either side

`npm audit --omit=dev` reports zero. `dotnet list package --vulnerable --include-transitive` reports
none across all seven projects.

### The debt that is already tracked

`BACKLOG-REMEDIATION.md` holds 110 identified items, **57 closed and 53 open**, each with a
reproduction, a confirmation point, a verdict and a size. `COMPLETION-INVENTORY.md` holds 142 surface
rows: 133 delivered, 3 missing, 5 refused, 1 unresolved.

Any debt pass that produces a fresh list without reconciling against those two documents is competing
with work already done. The 53 open items are the real backlog; what follows is what those documents do
**not** already contain.

## What the prioritiser said, and where it is wrong

The skill's prioritiser was run on the thirteen items above with WSJF, a four-person team and a
twenty-point sprint. Its top three:

1. The beta telemetry package (10.22)
2. HarfBuzzSharp (8.21)
3. ASP.NET Core patches (6.85)

Row-scoping — the Critical item — came **eighth**, below deleting the 343 MB of gitignored files.

That is WSJF behaving exactly as designed: it divides value by effort, so cheap items float. It is
still the wrong answer here, because the thing it ranked eighth is the one that leaks one
organisation's tenders to another and has no instrument watching it. A framework that cannot see that
should not be the one that decides.

Its effort model is also not evidence. It derived 630 hours from item type and severity alone, without
reading a line of this code.

## The order I would actually work in

**First, and on its own: a guard for row-scoping.** Not a refactor — an instrument. Every handler that
reads an organisation-scoped table should be provably filtered, and the cheapest honest version is an
architecture test over the handler bodies plus a fixture with two organisations that asserts the second
cannot see the first's rows. This repository already knows how to write that kind of test; it has
fourteen of them on the frontend alone. Until it exists, the rule the product most depends on is held
up by care.

**Second: the naming layer.** It is the only item on this list a user can see, it is already scoped by
the Rams audit, and it needs one decision — where a displayed name comes from — rather than a patch per
screen. Doing it screen by screen is how it got this way.

**Third: the four dependency items, together, in one pull request.** The ASP.NET Core patch gap is the
one that matters; the beta package and HarfBuzzSharp are decisions, not upgrades, and should be taken
deliberately while the patches are being applied anyway.

**Fourth: the two scoping gaps** — the staff invite with no organisation, and the evaluator layout with
no persona check. Both are small, both are currently invisible, and both are the same class of defect
as the first item.

**Not yet: the large files.** `RfqHandlers.cs` at 1,292 lines is the obvious candidate and the wrong
place to start. Splitting it changes no behaviour, risks the thing the tests are green about, and buys
readability in a file that is already heavily commented. Do it when something forces the file open.

**Not at all, for now: `i18n/config.ts`.** It is the largest file in the repository and the least
dangerous. Splitting the catalogues is a mechanical change that would touch every string in the product
and invalidate the one guard that compares the two languages. It should move only as part of the
naming work, if at all.

## What this pass could not establish

- **Whether the 53 open remediation items are still open.** They were reproduced when written; several
  sit in areas that have since shipped. Re-confirming them is a day's work and would sharpen the
  backlog more than anything else in this document.
- **Runtime performance.** Nothing here measured it. `perf/baseline.py` exists and has not been run
  against current data.
- **Whether the row-scoping gap has ever been exploited in the demonstration environment.** The audit
  log would answer it; nobody has asked.
