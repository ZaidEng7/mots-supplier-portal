### 0.2 Unresolved: **1**, named

**SCR-501 — Evaluation instructions / brief** (`evaluator`, P0). `MyEvaluationPage` renders each
criterion's name, weight and max score, and never renders the `guidance` text that
`EvaluationTemplate` criteria carry. `SCREEN-SPECIFICATIONS.md` mentions SCR-501 exactly once — as an
entry point in SCR-502's "Entry points" line — and never specifies it. So whether the criteria list
*is* the brief, or whether a brief is a separate thing carrying the guidance text, cannot be decided
from the documents. **It needs a person, not more grepping.** One row, honestly unresolved, is worth
more than a 35th confident "missing".

### The four items in no backlog file

Unbuilt scope rather than gaps against a spec, which is why they have gone uncounted. Sized here for
the first time.

#### 3.1 Full-text search — EPIC-20 · **M**

**What exists:** `SearchBuyerOfferingsHandler` (`OfferingHandlers.cs:188`) does
`EF.Functions.ILike` against `NameEn` and `NameAr` with the caller's text escaped as a LIKE pattern.
Category filtering and paging are real.

**What does not:** anything a person would call search. No `tsvector`, no ranking, no relevance
order (results are `orderby o.NameEn`), no stemming, no Arabic normalisation — and it reaches one
entity. Suppliers, RFQs, documents and offerings are not searchable together, which is what SCR-906
is. Two columns of one table is a filter with a text box.

**Size — M.** A `tsvector` column with a GIN index and a trigger per searchable entity, an Arabic
text-search configuration (the part most likely to surprise: Postgres has no built-in Arabic
dictionary, so this is a real decision, not a switch), a cross-entity result contract with row-scoping
per persona, and SCR-906. The row-scoping is the substance: a search that returns rows the caller
could not open directly is a disclosure, and it must be enforced per entity type.

#### 3.2 `Correlation-Id` request-header echo — EPIC-25 · **S**

**What exists:** `HttpAuditContext.CorrelationId` reinterprets `Activity.Current.TraceId` as a Guid,
so every audit row and every problem response carries a correlation id
(`Api/Errors/ProblemResponse.cs:45`).

**What does not:** the request header is never read. A client that sends `Correlation-Id: X` gets a
different id back, and cannot join its own log line to the server's. ASP.NET picks up W3C
`traceparent` automatically — which is a different header, and not the one a caller integrating
against this API would think to send.

**Size — S.** Read the header in middleware, validate it, seed the Activity or carry it alongside,
echo it on the response, and prefer it over the generated fallback. One middleware, one test asserting
the echo, one asserting a malformed value is ignored rather than trusted.

#### 3.3 Load and performance baseline — EPIC-26 · **M**

**What exists:** documented targets — p95 < 300ms reads, < 800ms writes
(`00-foundational-decisions.md:175`, restated in three more documents).

**What does not:** any measurement. No k6, no NBomber, no JMeter, no CI perf job, no recorded number
for any endpoint. The targets have never been tested against, so **it is not known whether they are
met, and no claim either way should be made.**

**Size — M.** A tool choice, a seeded dataset at a realistic scale (the interesting cases are the
cross-aggregate reads — the procurement dashboard and the comparison matrix), scripts for the read
and write paths, a baseline run, and a decision about whether it gates CI or runs on a schedule.
Gating on latency in a shared CI runner produces flakes, so scheduled-with-a-tracked-trend is the
likelier answer. **This item can change every other estimate here**, which is why it is ranked 11th
rather than last.

#### 3.4 OpenAPI generation and the CI contract gate — **M**

**What §11 documents** (`docs/api/API-ARCHITECTURE.md:415`): native .NET OpenAPI at
`/openapi/v1.json`; Scalar at `/scalar`; the doc as contract source for SPA type generation
(`openapi-typescript` → typed TanStack Query hooks) and the ERP ACL client; and **"CI fails on an
undocumented breaking diff (spectral/oasdiff gate)"**.

**What exists:** `builder.Services.AddOpenApi()` and `app.MapOpenApi()`, the latter inside
`if (app.Environment.IsDevelopment())`.

**What does not:** Scalar is not referenced anywhere in the API project. `openapi-typescript` is not a
frontend dependency — all 195 named endpoints are consumed through hand-written clients under
`src/frontend/src/api/`. And there is **no contract gate in CI at all**: `grep -n "openapi\|contract"
over `.github/workflows/ci.yml` returns nothing.

**This is the one with a history.** Every rename pass — R-9, §12-A/C, the batch-8 conformance sweep —
has leaned entirely on the test suites to catch a breaking wire change, because the safety net §11
describes has never existed. That worked, and it worked because those passes were careful, not because
anything enforced it.

**Size — M.** Publish the document outside Development, commit a baseline, add `oasdiff` against the
committed baseline in CI failing on a breaking diff, and add spectral for the style rules §11 lists
(every endpoint documenting its permission, its error `type`s, its pagination mode, whether it needs
`Idempotency-Key`/`If-Match`). The generation is small; **the work is making 195 endpoints satisfy
those four documentation requirements**, and the gate will fail loudly on day one until they do. Worth
knowing before it is started: this is a sweep, not a switch.

## 4. Two live rules that silently do nothing

Both are built. Both are tested. Neither has any effect, and neither is visible from any screen.
Confirmed against the code below.

### 4.1 BRULE-023 — the auto-suspend that suspends nobody

**The rule.** Expiry of an award-critical document suspends the supplier.

**The code.** `DocumentExpiryJob.cs:106` calls `AutoSuspendForAwardCriticalExpiryAsync` on every
document the run transitioned to `Expired`. The predicate is
`DocumentType.IsAwardCritical` — the job's own doc comment (`:140`) says it is
"driven entirely by … `IsAwardCritical`, which no seeded type sets."

**Confirmed.** `IsAwardCritical` is declared once outside migrations —
`Domain/ReferenceData/DocumentType.cs:31` — and read in exactly one place, this job. The migration
that introduced it (`20260829102041_DocumentTypeAwardCritical.cs`) adds the column with
`defaultValue: false` and then explicitly sets **`false` for all three seeded types**. There is no
admin surface that can set it either: `ReferenceDataPage` edits names and the active flag, and
`ReferenceItemPayload` carries `isRequired` and `expiryTracked` — not `isAwardCritical`.

**Verdict: a data decision first, then a small code gap.** The rule cannot fire until somebody decides
which document types are award-critical, and that is a ministry decision about procurement risk, not a
default anyone should invent — the job comment makes the same argument, and it is right: "was blocked
from participating for a fortnight" is not undone by reactivation. Once decided, the code gap is real
but small: the flag is not in the reference-data write contract, so even a ministry that has decided
cannot record it without a migration.

**Logged, not fixed** (this task changes no production code).

### 4.2 BRULE-016 — required documents ignore what the supplier does

**The rule.** Required documents are conditioned on the supplier's categories.

**The code.** Four call sites derive the required set from a flat two-column filter, with no reference
to category anywhere:

- `DocumentCompletenessEvaluator.cs:24, 45, 98` — `db.DocumentTypes.Where(t => t.IsRequired && t.IsActive)`
- `GetSupplierHandler.cs:42, 75` — `CountAsync(t => t.IsRequired && t.IsActive)`
- `SupplierDashboardHandler.cs:114` — the same count for the profile-health tile
- `ListSupplierDocumentsHandler.cs:34` — projects `t.IsRequired` straight through

**Confirmed, and it is worse than an unimplemented filter.** `Domain/ReferenceData/DocumentType.cs`
contains **no category field, no category collection, and no join entity** — `grep -n "Category"`
over it returns nothing. The condition BRULE-016 describes is not merely unapplied; it is
**unrepresentable in the schema**. Every supplier therefore sees an identical required-document list,
and the submit gate, the resubmit gate, the reviewer's approval gate and the dashboard's completeness
percentage are all computed from it.

**Verdict: both, and the code half is the larger.** The data decision is which document types attach
to which categories. The code gap is a `DocumentTypeCategory` join (or a category-code array on the
type), a migration, and then the filter change at all four call sites plus the two counts — and
`DocumentCompletenessEvaluator` is the shared gate for three separate flows, so this is a change to
what "complete" means for every supplier in the system, not a query tweak.

**One consequence worth stating before anyone starts:** suppliers already approved under the flat rule
were approved against a list that may not be theirs under a category-conditioned one. Whether tightening
applies retroactively is a decision, and it belongs with the data decision, not after it.

**Logged, not fixed.**
